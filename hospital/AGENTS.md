# Backend guidance

These instructions apply under `hospital/`.

Before making a backend implementation decision or edit, read the repository-root
`.agents/guidance/README.md` and
`.agents/guidance/02-backend-database-api.md`. Also read guide 01 for product
behavior or proposal compliance, guide 04 for database setup or reference data,
and guide 05 when behavior, schema, tests, or measured evidence must be reflected
in the report.

## Architecture and contracts

- Keep the existing Spring MVC flow: controller to service to repository. Put
  business decisions in services, not controllers.
- Expose request and response DTOs rather than JPA entities.
- Preserve `ApiResponse` and `PageResponse` shapes and the exception mapping in
  `GlobalExceptionHandler`.
- For routine in-scope work, choose the smallest design compatible with the
  existing code and implement it. Ask for design confirmation only when a
  missing choice would materially change behavior or scope.
- Apply Jakarta Validation to inbound DTOs and keep duplicate-field validation
  consistent with the current patient create and update flows.
- `spring.jpa.open-in-view=false`; do not depend on lazy relationships after the
  transaction has ended. Use explicit queries, projections, or service-layer
  mapping.
- Preserve the readable patient identifier generated by `PatientIdGenerator`.
  Do not replace it with a UUID or a database-generated numeric key.
- Preserve the current database-backed staff login in `APP_USERS`, stateless
  bearer JWT authentication, and permission-based RBAC enforced by Spring
  Security. Add new protected behavior through `AppPermission`, `UserRole`, and
  controller authorization rather than relying on frontend guards alone.
- Preserve the V19 Patient account invariant: one nullable unique
  `app_user_patient_id` belongs only to role `PATIENT`; staff accounts have no
  patient link, and Patient accounts are lifecycle-managed by patient CRUD.
  `GET /api/v1/patient-portal/me` must derive ownership from the authenticated
  account and must never accept a client-selected patient identifier.
- Treat the identity-card credential as temporary. Store only its BCrypt hash,
  expose only `CHANGE_OWN_PASSWORD` until replacement, increment token version
  on replacement or username change, and never disclose credentials in API or
  audit data.

## Persistence

- Oracle and Flyway are the supported database path.
- Add a new ordered migration for schema changes. Do not silently rewrite a
  migration that may already have been applied.
- Keep table-specific column prefixes and the constraints, sequences, indexes,
  and triggers established by existing migrations.
- Keep `PATIENT_HISTORY` as per-patient field-level update history. Keep
  `AUDIT_LOGS` as the business-event header for successful patient, admission,
  staff-account, and care-workflow writes. Keep ordered typed changes in `AUDIT_LOG_CHANGES`
  and ordered multi-record targets in `AUDIT_LOG_TARGETS`. Record the complete
  event through `AuditLogService` in the same transaction as the write, and do
  not audit reads, searches, navigation, login, or logout.
- Keep `GET /api/v1/audit-logs` server-filtered before pagination. Its optional
  criteria are `actor`, `search`, `action`, `entityType`, `from`, and `to`.
  Actor is an exact case-insensitive username or display-name match. Keyword
  search covers actor snapshots, resource and subject identities, details, and
  summary. Date boundaries are inclusive calendar dates, and `from` after `to`
  is invalid. Actor input has a maximum of 100 characters and keyword input has
  a maximum of 200 characters.
- Keep `GET /api/v1/audit-logs/{id}` under the same `VIEW_AUDIT_LOG` permission.
  It returns the event header with ordered changes and affected targets. Preserve
  version 1 list rows and detail responses through the explicit legacy fallback.
- Preserve sample provenance in both list and detail responses. V17 backfills
  the synthetic V16 rows from their stable marker, V18 sets the sample flag on
  every structured demonstration row, and runtime writes set it to false.
- Keep each version 2 summary concise and distinct from the event and target.
  Use a change summary such as `2 fields changed`, `Permanently
  deleted`, `2 records deleted`, `Active to Locked`, or `Credentials reset and
  existing sessions revoked`.
- Classify audit values before persistence. Redact `PERSONAL` and `MEDICAL`
  values, omit `SECRET` changes, and never persist credentials or tokens.
- Treat leading-wildcard audit search as unproven at enterprise scale until it
  has representative Oracle plans and load evidence. The audit tables are not
  append-only or tamper-evident, so production deployment requires restricted
  database grants and retention policy.
- Keep stable patient identity and personal information in `PATIENTS`. Department,
  doctor, and room assignments belong to the relevant admission, appointment,
  diagnosis, or prescription record rather than permanent columns on a patient.
  Derive a patient's current assignment from the active treatment episode when
  that information is needed.
- Preserve the table-specific status-flag semantics defined in the root
  `AGENTS.md`: filter inactive reference options from new-record choices without
  breaking historical reads, but do not treat the room-availability flag as a
  generic soft-delete flag.

## Verification

Run commands from `hospital/`:

```powershell
.\mvnw.cmd test
.\mvnw.cmd verify
```

Use `-Dtest=ClassName` for a focused test during iteration. Add or update service
and controller tests when behavior or API contracts change.
